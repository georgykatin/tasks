
## №1 Биржа фриланс заказов (или любых других)
+ Примерные кейсы
	+ Заказчит публикует задачу и платит за ней, получает отклики от исполнителей
	+ Исполнитель получает заказы , деньги после выполнения
	+ Система держит деньги в заморозке (или как угодно иначе) пока работа не завершена , система выступает своеобразным гарантом честности операции
 ---
+ Основные сложности 
	+ Задача должна быть в работе у одного, нельзя допустить дублирования для разных исполнителей
	+ Механизм получения оплаты от исполнителя и заморозки до момента выполнения задачи или отказа от выполнения и возврата денег
	+ Работа с конечными автоматами
	+ Интеграция веб-сокетов для риалтайм статусов работы
---
+ Примерный стек по технологиям
	+ SQL БД 
	+ Очередь (сразу скажу здесь и нужна, и нет , нужно выбрать и обосновать )
	+ Веб-сокеты (горилла, тут особо без альтернатив)
	+ jwt (обосновать почему и для чего)
	+ докер компоуз 
	+ Требования
	+ Реализовать работоспособный вариант
	+ Реализовать все требования по обсервабилити
	+ Проведение тестирования всем корнеркейсов, чтобы готовый вариант гарантированно не допускал дублирования задач между исполнителями, а все статусы гарантированно быстро обновлялись и попадали к получателю




## №2 Файловое хранилище (аналог Яндекс Диска)
+  Примерные кейсы
	- Пользователь регистрируется и получает личное хранилище с квотой (например 10 ГБ)
	- Загружает файлы - маленькие целиком, большие по частям (chunked upload)
	- Организует файлы в папки, переименовывает, перемещает, удаляет в корзину
	- Шарит файл или папку по ссылке с правами: только просмотр или редактирование
	- Скачивает файл - сервер стримит байты не загружая всё в память
	- Восстанавливает предыдущую версию файла если случайно перезаписал

---
 + Основные сложности
	- Загрузка по чанкам, загружает параллельно, сервер собирает обратно. Нужно хранить состояние загрузки и уметь возобновлять после обрыва
	- Нельзя читать файл целиком в память, всё через `io.Reader` / `io.Writer`,
	- Если два пользователя загружают один и тот же файл, физически хранить его нужно один раз.
	- Рекурсивные запросы, подсчёт размера папки включая вложенные, запрет циклических ссылок
	- У каждого объекта своя ACL, нужно проверять права на каждой операции включая вложенные файлы при шаринге папки
	- Атомарно проверить и занять место при загрузке, освободить при удалении

---
+ Примерный стек
	- SQL БД 
	- S3 хранилище
	- Cache 
	- Очередь
	- JWT
	- Docker Compose




## №3 Мониторинг цен

+ Примерные кейсы
	- Пользователь добавляет ссылку на товар и целевую цену - "хочу купить за X рублей"
	- Сервис регулярно проверяет цену на странице товара и сохраняет историю
	- Когда цена достигла цели - пользователь получает уведомление (email или webhook)
	- Пользователь видит график изменения цены за последние N дней
	- Можно отслеживать несколько товаров одновременно, управлять подписками
---
+ Основные сложности
	- Нельзя дудосить один сайт слишком часто, иначе забанят по IP. Нужен механизм как это обойти
	- Если сайт вернул 429 или 503, нужно подождать и повторить, но не бесконечно , нужно решить как именно и сколько ждать, как обрабатывать такие кейсы
	- Настраиваемый и управляемый воркер пул, обоснование сколько именно надо и как именно 
	- У большинства площадок нет открытого апи чтобы парсить цены, и у каждого магазина своя структура HTML, нужна гибкая система селекторов, также цена может быть `1 990 ₽` а не `1990` - нужна нормализация
	- Задачи на парсинг должны создаваться по расписанию, равномерно распределяться во времени чтобы не было спайков нагрузки
	- Если воркер упал на середине и задача вернулась в очередь, повторная обработка не должна создавать дублей в истории цен
	- Корректный механизм парсинга, не просто разные http.Get c готовой ссылкой, а именно механизм собственного парсера для каждой из площадок, плюс это покрывает обход разных антифрод решений у разных площадок(небольшая подсказка, я бы хотел тут видеть интерфейс парсера и разные реализации)

---
 + Примерный стек
	+  SQL БД  
	+  Cache — кэш последней известной цены, rate limiter по домену
	- Очередь
	- Метрики вне обсервабилити (метрики сколько активных задач на парсинг, сколько неуспешных попыток получения цены, время парсинга по доментам )
	- Трейсы от момента создания задачи до отправки уведомления
	- Docker compose 



## №4 Агрегатор новостей

+  Примерные кейсы
	- Система регулярно обходит список RSS-лент и забирает новые статьи
	- Похожие статьи из разных источников об одном событии - схлопываются в одну карточку
	- Каждая статья автоматически получает теги через AI API (технологии, политика, спорт и т.д.)
	- Пользователь выбирает интересующие теги и источники - видит персональную ленту
	- Лента пагинируется, есть полнотекстовый поиск по заголовкам и содержимому

---
+  Основные сложности
	- Одну новость публикуют 10 изданий. Не нужно дублировать её 10 раз, нужно заложить механизм как это делать. (Хеши или какой-то другой?)
	-  API нейросети упал или отвечает медленно. Нужен механизм как на нем не виснуть или например переключиться на другую , здесь же rate limiting к апи и оптимизация траты токенов, выбор достаточной модели
	- Полнотекстовый поиск  в PostgreSQL, правильные индексы
	- Оптимизировать хранение новостей, не нужно хранить старые, автоудаление

---
+ Примерный стек
	- SQL БД  
	- Очередь ( какая удобнее и лучше?)
	- AI API
	- Метрики на состояние очереди тегирования, процент дедупликации
	- Docker Compose


## №5 Сервис бронирования переговорок / коворкингов

+ Примерные кейсы
	+ Пользователь видит доступные переговорные комнаты на выбранную дату и время
	+ Может забронировать комнату на определённый временной интервал
	+ Может отменить или перенести бронь
	+ Несколько пользователей одновременно пытаются забронировать одну и ту же комнату
	+ Перед началом встречи пользователь получает уведомление
	+ Администратор может временно закрыть комнату на обслуживание

---
+ Основные сложности
	+ Нельзя допустить пересекающихся броней одной комнаты, даже если два запроса прилетели практически одновременно
	+ Нужно решить проблему race condition не через mutex внутри приложения, потому что приложение потенциально может быть запущено в нескольких экземплярах
	+ Нужно корректно работать с часовыми поясами и хранением времени
	+ Нужно продумать механизм временного hold, например пользователь начал оформление бронирования, но ещё не подтвердил его
	+ Hold должен автоматически протухать и освобождать слот
	+ Перенос бронирования должен происходить атомарно: нельзя сначала удалить старую бронь, а потом обнаружить, что новое время уже занято
	+ Нужно корректно получать список свободных интервалов без загрузки всех броней в приложение
	+ Уведомления о скором начале встречи должны отправляться гарантированно, но без дублей
	+ При нескольких репликах приложения обработка фоновых задач не должна приводить к многократной отправке уведомлений

---
+ Примерный стек
	+ SQL БД
	+ Redis — временные данные / cache, но необходимость использования нужно обосновать
	+ Очередь для уведомлений
	+ JWT
	+ Метрики количества конфликтов бронирования, активных hold, времени выполнения запросов поиска свободных слотов
	+ Трейсы процесса создание брони → подтверждение → уведомление
	+ Docker Compose


## №6 Сервис доставки заказов

+ Примерные кейсы
	+ Пользователь создаёт заказ на доставку
	+ Система подбирает свободного курьера
	+ Курьер принимает заказ и получает информацию о точках получения и доставки
	+ Пользователь в realtime видит статус заказа
	+ Курьер последовательно меняет статусы: назначен → едет за заказом → забрал → доставляет → доставлен
	+ Если курьер отказался или долго не принимает заказ, система ищет другого

---
+ Основные сложности
	+ Один заказ не должен быть одновременно назначен нескольким курьерам
	+ Один курьер не должен получить больше разрешённого количества активных заказов
	+ Нужно реализовать конечный автомат состояний заказа и запретить невозможные переходы, например delivered → created
	+ Назначение курьера должно корректно работать при нескольких экземплярах сервиса
	+ Нужно решить, как искать курьера: polling, очередь задач, события или другой механизм, и обосновать решение
	+ Курьер может получить заказ, после чего приложение потеряет соединение — состояние системы не должно зависеть от websocket соединения
	+ События изменения статусов должны гарантированно доходить до пользователя
	+ Повторная доставка сообщения из очереди не должна дважды менять состояние заказа
	+ Нужно предусмотреть timeout: курьер получил предложение, но ничего не ответил
	+ Желательно реализовать reconciliation механизм, который периодически ищет зависшие заказы и исправляет или возвращает их в обработку

---
+ Примерный стек
	+ SQL БД
	+ Redis — хранение краткоживущих данных / информации о доступности курьеров
	+ Очередь
	+ WebSocket
	+ JWT
	+ Метрики времени поиска курьера, количества неназначенных заказов, времени заказа в каждом статусе
	+ Трейсы от создания заказа до назначения курьера
	+ Docker Compose


## №7 Система обработки платежей / упрощённый платёжный шлюз

+ Примерные кейсы
	+ Пользователь создаёт платёж
	+ Система обращается к внешнему платёжному провайдеру
	+ Провайдер может сразу вернуть результат или прислать webhook позднее
	+ Пользователь может повторно запросить оплату после ошибки
	+ Можно выполнить возврат платежа
	+ Система хранит историю всех операций по платежу

---
+ Основные сложности
	+ POST запрос может быть отправлен клиентом несколько раз из-за timeout, но списание должно произойти только один раз
	+ Нужно реализовать полноценную идемпотентность операций через idempotency key
	+ HTTP timeout не означает, что операция у платёжного провайдера не выполнилась
	+ Нужно корректно обрабатывать ситуацию, когда ответ API говорит одно, а webhook позже сообщает другое состояние
	+ Webhook может прийти несколько раз, с задержкой или не по порядку
	+ Нельзя просто доверять webhook — необходимо проверять подпись
	+ Нужно реализовать конечный автомат состояний платежа
	+ Возврат денег также должен быть идемпотентным
	+ Нужен reconciliation job, который периодически сравнивает локальное состояние платежей с состоянием внешнего провайдера
	+ Изменение состояния в БД и отправка события другим сервисам должны быть согласованы, здесь желательно подумать про transactional outbox
	+ Денежные значения нельзя хранить в float

---
+ Примерный стек
	+ SQL БД
	+ Очередь
	+ HTTP интеграция с эмулятором платёжного провайдера
	+ Redis — опционально, необходимость использования обосновать
	+ JWT
	+ Метрики количества успешных / неуспешных платежей, reconciliation ошибок, webhook retry
	+ Трейсы полного lifecycle платежа
	+ Docker Compose


## №8 Сервис обработки изображений / видео

+ Примерные кейсы
	+ Пользователь загружает изображение или видео
	+ После загрузки система запускает несколько операций обработки
	+ Для изображения: resize, thumbnail, watermark, конвертация формата
	+ Для видео: получение metadata, preview, несколько вариантов качества
	+ Пользователь видит прогресс обработки
	+ После завершения получает ссылки на готовые файлы

---
+ Основные сложности
	+ HTTP запрос пользователя не должен ждать завершения тяжёлой обработки
	+ Обработка состоит из нескольких этапов, некоторые могут выполняться параллельно, некоторые только после предыдущего этапа
	+ Нужно решить, как хранить состояние pipeline обработки
	+ Если worker упал во время задачи, она должна быть выполнена повторно
	+ Повторное выполнение не должно создавать несколько одинаковых файлов
	+ Нужно ограничить количество одновременно выполняемых CPU / memory intensive задач
	+ Задачи разной тяжести не должны блокировать друг друга
	+ Большие файлы нельзя читать целиком в память
	+ Пользователь может удалить исходный файл, пока он ещё находится в обработке — нужно определить корректное поведение системы
	+ Нужно реализовать механизм отмены задачи
	+ Нужно корректно очищать временные файлы после падений worker
	+ Желательно реализовать приоритеты задач, например платные пользователи выше бесплатных

---
+ Примерный стек
	+ SQL БД
	+ S3
	+ Очередь
	+ Redis — состояние прогресса / cache, необходимость обосновать
	+ WebSocket или SSE для отображения прогресса
	+ JWT
	+ Метрики длины очереди, времени обработки, количества retry, количества failed jobs
	+ Distributed tracing для всего pipeline
	+ Docker Compose

## №9 Система продажи билетов на мероприятия

+ Примерные кейсы
	+ Организатор создаёт мероприятие и схему доступных мест
	+ Пользователь выбирает одно или несколько мест
	+ На время оплаты места резервируются
	+ После успешной оплаты пользователь получает билет
	+ Если оплата не прошла или пользователь ничего не сделал, места снова становятся доступными
	+ Пользователь может вернуть билет по правилам мероприятия

---
+ Основные сложности
	+ Популярное место одновременно могут попытаться купить сотни пользователей
	+ Одно место нельзя продать два раза
	+ Нельзя держать SQL транзакцию открытой несколько минут, пока пользователь вводит данные карты
	+ Нужен механизм временной reservation / hold с TTL
	+ Нужно корректно обрабатывать истечение reservation одновременно с успешной оплатой
	+ Покупка нескольких мест должна быть атомарной: либо пользователь получает все выбранные места, либо ни одного
	+ Оплата может завершиться после timeout или после истечения hold — нужно определить стратегию обработки такого состояния
	+ Повторные webhook от платёжной системы не должны повторно выпускать билет
	+ Необходимо продумать поведение системы при резком всплеске нагрузки в момент старта продаж
	+ Нельзя строить корректность только на Redis lock
	+ Выпуск билета и подтверждение покупки должны быть идемпотентными

---
+ Примерный стек
	+ SQL БД
	+ Redis
	+ Очередь
	+ Эмулятор платёжной системы
	+ JWT
	+ WebSocket / SSE для обновления доступности мест, необходимость realtime нужно обосновать
	+ Метрики количества hold, конфликтов бронирования, успешных и отменённых покупок
	+ Docker Compose


## №10 Система уведомлений

+ Примерные кейсы
	+ Другие сервисы создают уведомления пользователям
	+ Уведомление может быть отправлено через email, Telegram, webhook или другой канал
	+ Пользователь может настроить предпочтительные каналы
	+ Некоторые уведомления нужно отправить сразу, некоторые — в заданное время
	+ Можно создать массовую рассылку
	+ Пользователь может отключить определённый тип уведомлений

---
+ Основные сложности
	+ Один пользователь может получать уведомления через несколько каналов
	+ Отправка через внешний API может завершиться timeout, хотя сообщение фактически было отправлено
	+ Необходимо определить retry policy отдельно для разных каналов
	+ 4xx и 5xx ошибки нельзя обрабатывать одинаково
	+ Нужно реализовать exponential backoff + jitter
	+ Некоторые сообщения после определённого количества попыток должны попадать в DLQ
	+ Повторная доставка события из очереди не должна приводить к отправке нескольких одинаковых уведомлений
	+ Необходимо ограничивать скорость отправки отдельно для каждого провайдера
	+ Массовая рассылка на 100 000 пользователей не должна создавать мгновенный spike из 100 000 задач
	+ Нужно решить проблему scheduled notifications — как гарантированно отправить сообщение примерно в нужный момент
	+ Если пользователь отключил уведомления после создания задачи, но до её обработки, необходимо решить, отправлять её или нет
	+ Нужна возможность безопасно повторно обработать DLQ

---
+ Примерный стек
	+ SQL БД
	+ Очередь
	+ Redis — rate limiting / cache
	+ Несколько mock API провайдеров
	+ Метрики количества отправленных сообщений, retry, DLQ, latency отдельно по каждому провайдеру
	+ Трейсы create notification → queue → provider
	+ Docker Compose


## №11 Система аналитики событий / упрощённый Amplitude

+ Примерные кейсы
	+ Клиентские приложения отправляют события: page_view, purchase, signup и т.д.
	+ Система принимает большое количество событий и сохраняет их
	+ Пользователь может смотреть количество событий за выбранный период
	+ Можно группировать события по типу, пользователю, приложению и дополнительным параметрам
	+ Можно построить простую воронку signup → trial → purchase
	+ Можно получать realtime или почти realtime статистику

---
+ Основные сложности
	+ Поток записи значительно больше потока чтения, архитектуру нужно строить исходя из этого
	+ Нельзя выполнять тяжёлую аналитику непосредственно по основной transactional БД
	+ Нужно определить, что считать уникальным событием и как бороться с дублями
	+ Клиент может повторно отправить batch событий после timeout
	+ Нужно поддержать batch ingest
	+ События могут приходить не по порядку и сильно позже фактического времени возникновения
	+ Нужно разделять event time и ingestion time
	+ Агрегаты желательно считать заранее, но нужно определить какие именно
	+ При падении consumer события не должны теряться
	+ Необходимо продумать partitioning данных
	+ Нужно реализовать retention — например сырые события хранятся 30 дней, агрегаты значительно дольше
	+ Запрос одного пользователя не должен позволить ему получить события другого tenant
	+ При большом количестве значений пользовательских параметров можно столкнуться с проблемой высокой cardinality
